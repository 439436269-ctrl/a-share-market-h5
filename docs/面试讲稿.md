## 一、30 秒版本（自我介绍里带一句）

> 我最近做了一个 A 股行情移动端 H5，从零写了 WebSocket 行情推送层和 Canvas 图表引擎。传输层做了序号缺口检测和自动补拉全量；分时图和 K 线是完全不用第三方库、手写的 Canvas 渲染。前端用细粒度订阅把重渲染收敛到单只标的上。

**为什么这样设计这段话**：一句话覆盖三个岗位关键词（行情 / 稳定性 / 渲染），且每个都有可演示的证据，不给自己挖坑。

## 二、3 分钟完整介绍（分四段，按顺序说）

### 第 1 段 · 做了什么（30 秒）
自选列表（实时跳动）、个股详情（分时图 / 日 K / 五档盘口 / 成交明细）、交易状态机。
数据链路是：逐笔成交 → 1 分钟 bar → 日线。

### 第 2 段 · 分层与选型（40 秒）
- 三层：`market-core`（模型 / 协议 / 交易时段 / 指标，前后端共用）、`market-client`（连接层）、`server`（BFF + 网关）
- **必须有 BFF**：行情接口没有 CORS 头、还校验 Referer，浏览器直连必失败。而且行情源的降级逻辑应该收在服务端，前端只面对一种稳定契约。
- **零图表库**：分时图是这个品类里最高频最敏感的一张图，数据每秒都在追加，图表库的通用抽象（虚拟 DOM / 逐帧重建）反而成为负担。

### 第 3 段 · 两个最难的点（90 秒，这是重点）
**① 行情推模式和 React 响应式的冲突。**
行情是"高频、局部变化"：每 500ms 来一帧，一帧里通常只有几只票在动。常规写法是帧到达 → 顶层 setState → 整棵树重渲染。我把订阅粒度下沉到单个标的，每个行组件只订阅自己那一只，别的票跳动时它连 render 都不会被调度。底层用 `useSyncExternalStore`，它是 React 官方为外部可变数据源开的口子，自带撕裂防护。

**② 丢包不会让行情错下去。**
服务端是广播帧模型，每一帧带一个全局单调递增的 seq，**无论这帧有没有真的发出去，seq 都自增**。客户端校验 seq 连续性就能发现丢包，发现缺口后不"猜"、不试图补那一帧，而是直接发 resync 拉全量快照重建基线。另外心跳是独立的：TCP 连接可能"假活"，只靠 onclose 会一直挂着不重连，必须靠 pong 超时兜底。

### 第 4 段 · 业务上的处理（30 秒）
交易状态机由服务端下发，前端不本地猜，所以非交易时段按钮会自动禁用并给出原因；涨跌停价按板块幅度算（主板 10%、创业板科创板 20%、北交所 30%、指数无涨跌停）；盘口做了封板的语义——封涨停时卖盘为空、买一巨量排队，这是市场状态的正确表达，显示 `--` 是对的，补 0 是错的；配色按中国市场习惯红涨绿跌。

## 三、技术追问链（按最可能被追问的顺序）

### Q1｜行情数据怎么和 React 结合？不会一直重渲染吗？

**答**：订阅粒度下沉到单只标的 + 三字段判等（ts / last / volume），只有真的变了的标的才通知订阅者。

**追问 A：`useSyncExternalStore` 和 `useEffect + setState` 有什么区别？**
它是 React 官方为外部可变数据源提供的接口，天然处理并发渲染下的**撕裂（tearing）**问题——用 effect 桥接时，React 可能在一次渲染中读到两个不同版本的快照。另外它要求 `getSnapshot` 返回的是稳定引用，这点很关键。

**追问 B：判等为什么不深比较？**
行情对象本身是不可变的，同一帧里同一标的一个对象；比三个字段就够，深比较在每帧 30 个标的上纯属浪费。**这里踩过坑**：成交明细一开始永远不刷新，因为我在 `applyTicks` 里对数组原地 `unshift`，引用没变，React 认为快照没变。改成生成新数组就好了。React 的订阅靠引用比较，任何原地修改都是静默失败。

---

### Q2｜行情丢包、乱序怎么处理？

**答**：三条规则。
1. `seq === last + 1` → 接受
2. `seq <= last` → 乱序 / 重复帧，直接丢弃
3. `seq > last + 1` → 缺口，上抛事件、状态条切"缺口补拉中"、发 resync 拉全量重建基线

**追问：为什么不自己补那一帧？**
增量数据无法重放，缺就是缺。全量快照是唯一可靠的基线，试图按增量"缝"回去只会把错误扩散到盘口上。盘口一旦错一格，用户看到的买卖价就是错的。

**追问：如果反复缺口，会不会 resync 风暴？**
会，所以补拉做了节流（1 秒内只发一次）。

**追问：怎么发现链路"假死"？**
心跳。客户端每 15 秒发 ping，超过 40 秒没收到 pong 就判定链路已死、强制重连，不依赖 onclose。

**追问：重连会不会形成风暴？**
指数退避 + 全抖动：`min(30s, 500ms × 2^n)` 再取随机抖动，避免所有客户端在同一毫秒一起回来。

**追问：重连之后页面为什么还有数据？**
订阅集合是客户端的状态，不随连接销毁。重连成功后会把订阅集合重放一遍，并要求一份全量快照——这就是"订阅恢复"。

### Q3｜K 线渲染性能怎么优化？

> 这题要**分层答**，先说清什么量级才需要上什么手段，直接说"上 WebGL"是减分的。

**先给现状**：目前 160 根日线、240 根分时，Canvas 全量重绘一帧不到 2ms，完全不需要优化。所以下面讲的是量级上来的路径。

**第一层 · 减少绘制量**
- 虚拟窗口：只画可见区的 bar，其余不参与绘制
- 把蜡烛合并成一条 path 批量绘制，减少 draw call
- 十字光标用**独立的 overlay canvas**，移动时不重绘主图

**第二层 · 减少重绘频率**
- rAF 合帧：一帧内多次数据更新只重绘一次
- 只在数据真正变化时重绘，而不是 setState 就重绘
- 静态部分（网格、坐标轴）预渲染到离屏 canvas，每帧只 blit

**第三层 · 换渲染后端**
- OffscreenCanvas + Web Worker：把绘制挪出主线程，避免与行情解析抢主线程
- WebGL：蜡烛可以合并成一个三角形批次一次画完；十万根级别才有必要
- 数据层用 TypedArray 存 OHLCV，指标计算放 WASM

**最后给一个可量化的口径**：我会用 FPS / 长任务时长 / 内存峰值三个指标测，而不是只说"变快了"。

### Q4｜你怎么理解行情数据的时间语义？

**答**：四个层面。
1. **交易分钟坐标系**：分时图的 x 轴是"第几个交易分钟"，不是自然时间。09:30 是 0，11:30 是 119，**13:00 是 120**，午休不占位。这个坑我真实踩过——播种数据按连续分钟排时间戳、实时逐笔按墙上时钟算，两套口径对不上，归并永远命中不了同一根 bar，分时图就碎成一堆柱子。修复方式是统一到单一的 `sessionSlotToEpoch()`。
2. **交易所时钟 vs 本地时钟**：价格上的时间戳应该用交易所时钟，并且 UI 上明确标"更新于 hh:mm:ss"，让用户知道数据新鲜度。
3. **交易状态**：由服务端下发状态机（集合竞价 / 连续竞价 / 午间休市 / 收盘集合竞价 / 已收盘），前端不用本地时间猜。
4. **除权除息**：分红送股会让价格跳空，涨跌幅基准是**经过除权处理的昨收**，不是昨天的收盘价原始值。

### Q5｜前端怎么保证下单不会重复提交？

> M5 已实现，可以指着代码讲。

**答**：核心是**幂等键的生成时机**，不是"点两下拦一下"。

1. **幂等键绑定参数指纹**：用户点"确认"时生成 `clientOrderId`，参数不变就一直复用，参数一改就换新的。
   超时或失败重试必须复用同一个键，服务端幂等表命中后返回原委托，不会重复下单。
2. **超时不算失败**：请求超时时**绝不能换一个键重发** —— 请求可能已经到达服务端。复用同一个键重试才是安全的。
3. **同键换参数必须显式报错**：那是客户端 bug，静默返回旧单只会让问题更难查（`CLIENT_ORDER_ID_CONFLICT`）。
4. **按钮状态矩阵**：提交中自己转圈 + 改文案，且不允许重复点击；转圈表示"进行中"，置灰表示"不可用"，两者语义不同。
5. **二次确认**：确认页必须带全关键参数（方向、类型、价格、数量、预计金额、预计费用、冻结资金）。

**追问：校验放在前端还是后端？**
两边都放，但**用同一份代码**：`validateOrder` 是 `market-core` 里的纯函数，前端 `onChange` 调它做即时提示，服务端收到请求再调它做最终裁决。
前端校验只是体验，**服务端校验才是边界 —— 前端可以被绕过**。规则只有一份，就不会漂移。
它覆盖：交易时段、停牌、指数不可交易、申报单位（分板块）、涨跌停、**价格笼子 ±2%**（仅连续竞价生效）、可用资金、可用持仓。

**追问：冻结怎么管？**
两套：买入冻**资金**（金额 + 费用），卖出冻**股份**（扣 `available`，`volume` 不动）。
成交时按比例释放，差额退回可用；**终结（成交完/撤单）时必须把剩余冻结释放干净**，漏一处可用资金就永久少一块。
`T+1` 体现在"当日买入只增 `volume` 不增 `available`"。

**追问：交易回报和行情数据能共用一套机制吗？**
不能，语义不同：行情是"广播 + 可丢 + 可全量补拉"，交易回报是"用户私有 + 必须逐条送达"。
所以两者共用一根 WebSocket，但交易回报**不走行情帧的全局 seq**，也不受订阅集合过滤 —— 委托状态和你订阅了哪些标的一点关系都没有。

## 七、一句话记住这个项目的"魂"

> **行情前端的核心不是画图，是让用户相信他看到的那个数字是对的。**
> 所以这个项目里最重的部分全在"可靠性"上：seq 缺口补拉、心跳假死探测、订阅恢复、派生字段自洽、交易状态由服务端下发。
